# 性能测试方案与结果

状态：尚未实现独立 TCP 压测工具，尚未运行服务端性能压测。P2 已有真实 TCP 功能测试（16 连接各 10 次 ECHO）和关闭竞态重复回归；这些不是容量/吞吐基准。当前无吞吐量、P50/P95/P99、最大并发容量或可靠投递成功率数据。

## 两类模式

1. 纯网络模式：测试长度前缀、Protobuf、连接调度与回包，不访问数据库，不宣称测得持久化吞吐量。
2. 业务模式：登录、单聊、MySQL 提交、持久化 ACK、收件端本地事务与投递 ACK。报告多阶段延迟，不混用 send() 返回与业务完成。

## 测试矩阵

逐步增加 100、1000、5000 连接；根据机器资源决定是否继续。分别改变消息大小、单连接发送速率、IO 线程数、业务线程数、数据库池容量。每次仅改变一个主要变量，包含预热、稳定采样和冷却。

至少包含低速/慢读客户端、突发流量、离线用户、重连风暴、队列满、Redis 不可用和数据库抖动场景。负载发生器使用闭环和开放速率两种模式，说明背压、超时以及是否存在协调遗漏。

## 原始记录格式

每轮记录：日期、Git revision、CPU/内存/内核、编译器/优化级别、依赖版本、配置、数据集、warmup/采样时长、发出/接受/持久化/投递/失败/超时数量。

报告活跃连接、消息/秒、端到端 P50/P95/P99、CPU、RSS、错误率、投递成功率。延迟使用单调时钟和明确的开始/结束事件，跨机器时钟不同步时不直接相减。超时请求要进入失败和延迟解释，不能从分位数中悄悄删除。

perf 结果关联到同一轮原始数据，优化前后使用相同场景。`perf stat`、`perf record` 尚未运行；ASan/UBSan 已用于 P2 正确性测试，结果见 progress.md，不能代替 Release 性能基准。
